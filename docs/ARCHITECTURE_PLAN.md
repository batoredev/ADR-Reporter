### Changes in revision 2
1. **Seven** demo reviewer accounts forming a shared institutional review pool.
2. **Approval** needs a completed checklist. Information that is genuinely unavailable can be acknowledged with a reason instead of resolved. General notes never block approval.
3. **Urgent escalation pathway** for potentially serious ADRs. Incomplete reports can reach designated personnel without waiting for routine approval.
4. **Returned reports** go back to the same reviewer by default. **Release and reassignment** are both supported.
5. **Multiple seriousness criteria** can be selected.
6. **Basic external submission tracking**. It records what happened outside the app and never performs a submission.
7. **AI integration is configurable** (provider and model set in configuration), not tied to one model.
8. **AI prescription extraction moves up** to Step 3, right after the structured form. The review system follows.
9. **Approximate dates** are never written into the official form with ambiguous placeholders.

## 1. Scope

### In scope

**Priority 1: reporting, review and output**
1. Healthcare-professional login (demo accounts) and **structured** ADR reporting (form sections A–D).
2. Saving drafts and submitting to a **centralized review queue**.
3. **Shared review pool** of seven authorized reviewers:
   - claim, release and reassign cases
   - verify with a checklist (with reasoned exceptions)
   - comment
   - **approve** or **return for correction**; the reporter corrects and resubmits
4. **PvPI-aligned PDF** generated by filling the official form. All AMC/NCC-only identifiers stay blank.
5. **Seriousness flags, priority display and an urgent escalation pathway.**
6. **Basic external submission tracking** (method, destination, date, reference, acknowledgement).

**Priority 2: the AI demo, built as soon as the structured form works (Step 3)**

7. Upload a fictional prescription, extract the medication details, have the user verify them, and populate the ADR fields. The AI provider and model are configurable.

### Deferred (not built now)
- Production hosting, institutional login (SSO), cloud storage
- Email/SMS notifications. In-app alerts *are* included for escalations.
- On-hold status
- Formal second-opinion workflow
- Guided (question-based) reporting
- AI narratives and AI consistency checks
- Admin user-management screens (demo accounts come from a seed script)
- A full version-comparison screen. Versions are stored, and resubmitted changes are highlighted.

### Ground rules
- No invented clinical facts, fields, dates or official identifiers.
- These are **always blank** on the PDF:
  - AMC Report No.
  - Worldwide Unique No.
  - Reg/IPD/OPD/CR No.
  - receiving-personnel signature and name
  - the causality column
- Approval ≠ proof of causality. Downloading or printing ≠ submission to PvPI. Recording an external submission ≠ the app sending anything.
- Internal approval never blocks urgent escalation.
- No invented deadlines. Elapsed time is shown; target times are institution settings, empty by default.
- If AI is not configured, the app says so and manual entry still works.

## 2. What the official form dictates (inspected before mapping)

The PvPI form is a **fillable PDF** with 147 fields on page 1: 127 text, 19 checkboxes and 1 signature image. Page 2 is reporting advice.
The field names are generic (`Text Field0`…), so every field was mapped by position on the rendered page. The map was verified by a test fill: all 147 fields are accounted for, with no gaps and no duplicates.

| Form fact | How the prototype handles it |
|---|---|
| Fillable official form | The PDF is produced by **filling the official form**, not by redrawing it. |
| Auto font size in every field | Fixed small font (≈8 pt). |
| Room for 4 suspected medicines, 3 concomitant products; small text boxes | Overflow goes on a **continuation page** ("# Use separate page"). The page-1 cell says "See continuation sheet". |
| Initial / Follow-up Case boxes | Prototype reports are initial cases. Follow-ups are deferred; the box is not ticked. |
| No separate "reaction term" box; item 7 is "Describe Event/Reaction management" | Mandatory **Reaction term(s)** field, printed first in item 7, then description, then management. |
| Item 11 excludes products used to treat the reaction | "Used to treat the reaction" checkbox on concomitant products. Those print under item 7 (management). |
| Items 9 and 10 are tick cells | One choice per suspected medicine, printed as "X". |
| "FOR AMC / NCC USE ONLY" box, receiving-personnel signature | Never filled. Enforced in code and by an automated test. |
| Reporter "Signature" | Left blank for a handwritten signature. |
| Causality column (page 2: done at AMCs with the WHO-UMC scale) | Always blank. |
| Mandatory fields (page 2, E): patient initials, age at onset, reaction term(s), onset date, suspected medication(s), reporter information | These must be complete before **Submit for institutional review**. Urgent escalation doesn't need them (see §7). |
| Seriousness: No/Yes + 6 criteria (+ death date) | Any number of criteria can be ticked. Any criterion marks the case **potentially serious**. |
| Dates as dd/mm/yyyy | See the date rules below. |

### Date rules (no ambiguous placeholders)
Each date is stored with its **precision** (exact day / month and year only / year only) and an **"approximate"** flag. Unknown dates are marked explicitly. The app never invents a missing day or month. In particular, it never fills one in as `01`.

| What the reporter knows | Stored as | Printed in the official form box |
|---|---|---|
| Exact date | 2026-10-14 | `14/10/2026` |
| Month and year only | 2026-10 (month precision) | `Oct 2026`: the month in words, no dashes, no zeros, no made-up day |
| Year only | 2026 (year precision) | `2026` |
| Approximate ("around 14 October") | 2026-10-14 + approximate | `approx. 14/10/2026` |
| Explicitly unknown | unknown flag | `Unknown` |
| Not entered | nothing | blank |

- **Doesn't fit:** if a qualified date doesn't fit its box, the box reads "See additional information". The full statement goes in *Additional Information* or on the continuation page, e.g. "Reaction start date: approximately mid-October 2026 (reporter estimate)".
- **Comparisons:** date checks (such as "reaction before drug start") compare the *range* a partial date covers. "Oct 2026" is never treated as 1 October.

## 5. Data model (Prisma)

- **Institution**: name, department, case-number counter, optional urgent-acknowledgement target (empty by default).
  - Every query is filtered by the logged-in user's institution.
- **User**: name, email, password hash, roles, designation, occupation, address, PIN, phone, `isUrgentContact`, `canReassign`.
- **Session**: hashed token, user, expiry.
- **AdrCase**:
  - case number, status, reporter, assigned reviewer, claimed at, submitted / approved timestamps, current version, `lockVersion` (stops two people overwriting each other)
  - the single-value form sections (patient, reaction, history, seriousness incl. multiple criteria, outcome, additional information)
  - reporter snapshot (taken at submission)
  - `unknownFields`: the fields explicitly marked "Unknown"
- **Date fields**: each stored as `…Date` (text with precision: `YYYY`, `YYYY-MM` or `YYYY-MM-DD`) + `…DateApprox` (yes/no).
- **SuspectedMedicine**, **ConcomitantProduct**, **Investigation**: ordered rows, each with its own `unknownFields`.
- **CaseVersion**: frozen JSON snapshot at every submit, resubmit and approval.
- **CaseAssignment**: history of claims, releases and reassignments (who, to whom, reason, when).
- **ReviewChecklistItem**: per version, one per item (patient data, reaction chronology, suspected medication, clinical evidence, seriousness/outcome, reporter and mandatory completeness).
  - Outcome is **Verified** or **Verified with exception**. An exception needs a reason, e.g. "Batch number genuinely unavailable".
- **ReviewComment**:
  - kind **Note** (never blocks) or **Issue** (a discrepancy or request for information)
  - an Issue is **Open**, **Resolved**, or **Acknowledged – information unavailable** (reason required)
  - can be general or attached to a field
- **ReviewDecision**: approve or return, reviewer, reason (required for return), version, time.
- **UrgentEscalation**: case, raised by, raised at, urgency note, frozen snapshot of what was known, acknowledged by/at, closed by/at with note.
- **ExternalSubmission**:
  - kind: *routine* (after approval) or *urgent notification* (from an escalation, approval not needed)
  - method: AMC by email, AMC by hand, NCC email `pvpi.ipc@gov.in`, PvPI helpline, ADRPvPI app, other
  - destination, date/time, recorded by
  - external reference **only if provided by the recipient**
  - notes; acknowledgement date, reference and notes
- **AI records**:
  - **UploadedDocument**: file, type, size, hash, uploader.
  - **ExtractionRun**: document, provider, model, status, error, raw response.
  - **ExtractedItem**: field, proposed value, text as seen, uncertain flag, status (pending / accepted / edited / rejected), final value, decided by/at, target medicine row.
- **FieldProvenance**: per field, its source (entered by user / extracted from document + verified), document, verifier, time.
- **AuditLog**: append-only (a database trigger blocks UPDATE and DELETE). Records actor, action, case, before/after values and time.

## 6. Status flow

```
Draft ──submit──▶ Submitted ──claim──▶ Under review ──approve──▶ Approved ──record──▶ Externally submitted ──record──▶ Acknowledged
                     ▲                    │    ▲                (ready for external submission)
                     │               return│    │claim / reassign
                     │                    ▼    │
                Resubmitted ◀──resubmit── Returned for correction
```

- **Submit:** enabled only when the mandatory fields are complete. Freezes version 1.
- **Claim:** one atomic update that succeeds only if the case is unassigned. Concurrent clicks give exactly one winner.
- **Release:** the assignee puts the case back in the pool.
- **Reassign:** the assignee can hand the case to a named reviewer, and a queue lead can reassign any case. Both need a reason, and both are logged in the assignment history.
- **Return:** a reason is required. The case stays with the same reviewer by default, and the reporter edits it without losing version 1.
- **Resubmit:** freezes the next version. It goes back to the same reviewer, who sees the changed fields highlighted. Release and reassignment remain available.
- **Approve** requires:
  1. all six checklist items recorded for the current version, each Verified or Verified with exception with a reason
  2. no **Open** issues: each is Resolved, or Acknowledged as unavailable with a reason

  Notes never block. Approval freezes the final version and PDF.
- **Externally submitted / Acknowledged:** recorded by a coordinator. The app only records them; it never sends anything.
- **Who:** a reviewer cannot approve a report they wrote. Every transition is checked on the server and logged.

## 7. Seriousness, priority and urgent escalation

**Flags and priority**
- Ticking any seriousness criterion (several are allowed) or "Serious: Yes" marks the case **potentially serious**. The flag comes only from what the reporter ticked; there is no automatic text detection.
- **Queue:**
  - a red **Potentially serious** label naming the criteria
  - always sorted to the top, then oldest first
  - "time since submission" column
  - "serious only" filter
- **Dashboard:** a count of potentially serious cases and of open escalations.

**Urgent escalation pathway** (runs alongside routine review, never waits for it)

1. **Raising an escalation.** When a case is potentially serious, the reporter sees **Escalate urgently**, even on an **incomplete draft**. The only requirements are:
   - at least one seriousness criterion ticked
   - a short urgency note (e.g. "Patient admitted to ICU; full details to follow")

   Any reviewer can also escalate a submitted case.
2. **What it does:**
   - freezes a snapshot of what is known at that moment
   - timestamps it
   - shows an in-app alert to every **urgent contact**: a red banner and an **Urgent escalations** page with time since escalation
   - records everything in the audit log
3. **Designated personnel** can open escalated cases even while they are drafts. Normally drafts are private to the reporter. They can:
   - **acknowledge** receipt (timestamped)
   - contact the reporter or add a comment
   - **record an urgent notification** made outside the app (method, destination, time, reference), without waiting for approval
   - **close** the escalation with a note
4. **Afterwards:** the report continues the routine path (complete → submit → review → approve), and escalation details stay visible on the case.
5. **Timing:** elapsed time is shown. An acknowledgement target can be set per institution; it is empty by default, with no invented deadlines.

## 9. PDF generation
1. Fill the official `ADRRF_2.pdf` via the field map (8 pt text, checkboxes, "X" tick cells, dates per the date rules in §2).
2. These are always blank, with an automated test to guard them: AMC Report No., Worldwide Unique No., Reg/IPD/OPD/CR No., receiving personnel, causality, and reporter signature.
3. Add a continuation page for overflow rows, long text and date qualifiers that don't fit.
4. Print an internal reference in the bottom margin, outside the official fields: `Internal ref ADR-001 · v2 · generated 22/10/2026`.
5. Until approval, add a **DRAFT – NOT FOR SUBMISSION** watermark. The approved PDF is frozen (form flattened, stored, never regenerated with different data).
6. Keep page 2 (official advice) unchanged.
7. Test by filling the form, reading every field back and comparing; plus a visual check against the blank form.

## 10. AI prescription extraction (Step 3)

**Flow:**
1. In section C the reporter clicks **Extract from prescription** and uploads a JPG, PNG or PDF (max 10 MB). The type is checked by content, and the file is stored privately.
2. The server calls the configured `AiProvider`, which must return JSON matching a Zod schema. For each medicine:
   - name, strength, dose, route, frequency, start date, duration
   - manufacturer, batch and expiry (usually absent on prescriptions, so returned empty)
   - the exact text read
   - an "uncertain" flag

   The instructions forbid guessing.
3. **Verification screen:** the document sits beside the proposed values.
   - Each value is **accepted**, **edited** or **rejected**. Uncertain values need an explicit tick before they can be accepted.
   - The reporter marks each medicine as **suspected** or **concomitant**; the AI never decides that.
   - Nothing enters the report until **Add to report** is clicked.
4. Accepted values fill the medicine rows, with provenance recorded: "prescription.png · AI-extracted (provider/model) · verified by … at …". Reviewers see the source document beside those values (Step 4).
5. **Safeguards:**
   - not configured → "AI extraction unavailable – enter details manually"
   - refusal, unreadable output or an error → a clear message, never a silent partial fill
   - fictional prescriptions only
6. **Samples:** 2–3 fictional prescriptions (watermarked *FICTIONAL*): one clean and one low-quality "scan".
7. **Tests:** automated tests use a saved example response (no API calls, no cost). One live check is run with your key.
