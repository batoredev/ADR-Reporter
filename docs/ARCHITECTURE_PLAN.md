## 1. Scope

### In scope (in priority order)
1. Healthcare-professional login (demo accounts) and **structured** ADR reporting (form sections A–D).
2. Saving drafts and submitting to a **centralized review queue**.
3. **Shared review dashboard** for several authorized reviewers: claim a case, verify it with a checklist, comment, **approve** or **return for correction**; the reporter corrects and resubmits.
4. **PvPI-aligned PDF** generated by filling the official form. All AMC/NCC-only identifiers stay blank.
5. **Seriousness flags and priority** display.
6. *After 1–5 work end-to-end:* **AI prescription demo.** Upload a fictional prescription, extract the medication details, have the user verify them, and populate the ADR fields.

### Deferred (not built now)
- Production hosting, institutional login (SSO) and cloud storage
- Notifications and escalation
- On-hold and second-opinion actions
- External submission tracking (coordinator)
- Guided (question-based) reporting
- AI narratives and AI consistency checks
- Admin user-management screens (demo accounts come from a seed script)
- A full version-comparison screen. Versions *are* stored, and resubmitted changes are highlighted.

### Ground rules (from the spec and your instructions)
- No invented clinical facts, fields or official identifiers.
- AMC Report No., Worldwide Unique No., Reg/IPD/OPD/CR No., receiving-personnel signature/name and the causality column are **always blank** on the PDF.
- Approval ≠ proof of causality. Downloading or printing ≠ submission to PvPI.
- If no AI key is configured, the app says AI is unavailable and manual entry still works.

## 2. What the official form dictates (inspected before mapping)

The PvPI form is a **fillable PDF** with 147 fields on page 1 (127 text, 19 checkboxes, 1 signature image). Page 2 is reporting advice.
The field names are generic (`Text Field0`…), so every field was mapped by its position on the rendered page. The map was verified by a test fill: all 147 fields are accounted for, with no gaps and no duplicates.

| Form fact | How the prototype handles it |
|---|---|
| Fillable official form | The PDF is produced by **filling the official form**, not by redrawing it. |
| Auto font size in every field | Use a fixed small font (≈8 pt) so text is neither huge nor microscopic. |
| Room for 4 suspected medicines, 3 concomitant products; small text boxes | Extra rows and overflowing text go on a **continuation page**, as the form instructs ("# Use separate page"). The page-1 cell then says "See continuation sheet". |
| Initial / Follow-up Case boxes | Every report is an **Initial Case** in the prototype. Follow-ups are deferred, and the box is not ticked. |
| No separate "reaction term" box; item 7 is "Describe Event/Reaction management" | A mandatory **Reaction term(s)** field, printed first in item 7, then the description, then management. (The form's page 2 lists reaction term as mandatory.) |
| Item 11 excludes products used to treat the reaction | Concomitant products have a "used to treat the reaction" checkbox. Those print under item 7 (management), not item 11. |
| Items 9 (action taken) and 10 (rechallenge) are tick cells | One choice per suspected medicine, printed as "X". |
| "FOR AMC / NCC USE ONLY" box, receiving-personnel signature | Never filled, enforced in code and by an automated test. |
| Reporter "Signature" | Left blank for a handwritten signature. Login is not a signature. |
| Causality column (page 2: done at AMCs with the WHO-UMC scale) | Always blank in the prototype. |
| Mandatory fields (page 2, E): patient initials, age at onset, reaction term(s), onset date, suspected medication(s), reporter information | These are the rules that must pass before **Submit** is enabled. |
| Seriousness: No/Yes + 6 criteria (+ death date) | Stored as given. Any criterion marks the case **potentially serious**. More than one criterion can be ticked. |
| Dates as dd/mm/yyyy | Dates can be exact or approximate (month/year or year only) and print as e.g. `--/10/2026`. |

| Form item | App field | Mandatory |
|---|---|---|
| 1 Patient initials | `patientInitials` | ✓ |
| 2 Age or DOB | `ageAtOnset` (value + unit: years/months/days) **or** `dateOfBirth` | ✓ (one of them) |
| 3 Gender | `gender` (M / F / Other / not reported) | |
| 4 Weight | `weightKg` | |
| 5, 6 Reaction start / stop | `reactionStartDate` / `reactionStopDate` (or "ongoing") | start ✓ |
| 7 Description & management | `reactionTerms` ✓, `reactionDescription`, `reactionManagement` | terms ✓ |
| 8 Suspected medicine (repeatable) | name, manufacturer, batch/lot, expiry, dose, route, frequency, start, stop, indication | ≥1 with name ✓ |
| 9 Action taken | per medicine: withdrawn / increased / reduced / not changed / not applicable / unknown | |
| 10 Rechallenge | per medicine: yes / no / effect unknown / not reintroduced, + dose if reintroduced | |
| 11 Concomitant (repeatable) | name, dose, route, frequency, start, stop, indication, "used to treat reaction" | |
| 12 Investigations (repeatable) | test, result, date | |
| 13 History | free text + quick ticks (allergies, pregnancy, addiction, hepatic, renal) | |
| 14 Seriousness | serious yes/no/unknown, criteria, death date | |

## 3. Technology

| Layer | Choice |
|---|---|
| App | **Next.js 16** (App Router) + **TypeScript**, React Server Components + Server Actions |
| UI | **Tailwind CSS v4**, **shadcn/ui** components, **Lucide** icons, **Inter** font |

| Database | **PostgreSQL 16** (local) + **Prisma 7** (stable release; not the 8.0 release candidate) |
| Login | Simple email + password: bcrypt-hashed demo passwords, a session stored in the database, an httpOnly cookie. No external auth service. |
| PDF | **pdf-lib**, server-side, filling `ADRRF_2.pdf` with the verified field map |
| Uploads (AI demo) | Saved to a private folder on disk (`storage/uploads/`), outside the public web folder, and served only to logged-in users allowed to see the case |
| AI (demo) | **Anthropic Claude API** via `@anthropic-ai/sdk`, model `claude-opus-5-5`. Image and PDF input, structured JSON output validated with Zod (`messages.parse` + `zodOutputFormat`). Code sits behind a small `extractMedications()` interface so the provider can be swapped. |
| Tests | **Vitest** (unit/integration) + **Playwright** (end-to-end in a real browser) |

Exact package versions are pinned when installing.

## 5. Data model (Prisma, prototype)

- **Institution** has many users and cases. Every query is filtered by the logged-in user's institution.
- **User**: name, email, password hash, roles (`REPORTER`, `REVIEWER`), occupation, address, PIN, phone, designation.
- **Session**: hashed token, user, expiry.
- **AdrCase**:
  - case number (`ADR-001`…), status, reporter, assigned reviewer, claimed at, submitted at, approved at, current version number
  - `lockVersion`, to stop two people overwriting each other
  - the single-value form sections (patient, reaction, history, seriousness, outcome, additional information)
  - `unknownFields`: the list of fields the reporter explicitly marked "Unknown". These print as "Unknown"; empty fields stay blank.
- **SuspectedMedicine** (ordered rows), **ConcomitantProduct** (ordered rows), **Investigation** (rows).
- **CaseVersion**: frozen JSON snapshot taken at every submit, resubmit and approval. Used for "what changed" highlighting and for the approved PDF.
- **ReviewChecklist**: per version, six items (patient data, reaction chronology, suspected medication, clinical evidence, seriousness/outcome, reporter and mandatory completeness), plus who ticked them and when.
- **ReviewComment**: general or attached to one field, author, time, resolved by/at.
- **ReviewDecision**: approve or return, reviewer, reason (required for return), version, time.
- **AuditLog**, append-only. Records: created, edited, submitted, claimed, released, commented, returned, resubmitted, approved, PDF generated, document uploaded, extraction accepted. Each entry has actor, time, case, and before/after values where relevant. There is no edit or delete path in the app.
- *AI demo:*
  - **UploadedDocument**: file, type, size, uploader, case.
  - **ExtractedField**: proposed value, text as seen on the document, "uncertain" flag, and status (pending / accepted / edited / rejected). Also the final value, plus who verified it and when.

## 6. Status flow (prototype)

```
Draft ──submit──▶ Submitted ──claim──▶ Under review ──approve──▶ Approved
                     ▲                      │
                     │                 return (reason)
                     │                      ▼
                Resubmitted ◀──resubmit── Returned for correction
                 (goes back to the same reviewer)
```

- **Submit** is enabled only when the mandatory fields are complete; the form shows "Ready to submit". It freezes version 1.
- **Claim** ("Take up this case") is one atomic database update that succeeds only if nobody holds the case. If two reviewers click together, one gets it and the other sees "Already taken by …". The reviewer can **release** the case back to the queue.
- **Return** needs a reason. The reporter edits the same case; nothing from version 1 is lost.
- **Resubmit** freezes the next version. The reviewer sees changed fields highlighted against the previous version.
- **Approve** requires the checklist to be completed and all comments resolved. It freezes the final version and the final PDF.
- Every transition is checked on the server (role, owner, current state) and logged.
- A reviewer cannot approve a report they wrote.

## 7. Seriousness and priority

- **Reporter side:** ticking any seriousness criterion (or answering "Serious: Yes") shows a notice: "This report will be flagged potentially serious and prioritised for review."
- **Queue:**
  - potentially serious cases show a red **Potentially serious** label with the criteria named
  - they are always sorted to the top, then oldest first
  - a "time since submission" column is shown (e.g. "3 h")
  - there is a filter for serious cases only
- **Dashboard:** a count card for potentially serious cases.
- **Wording:** the flag says *potentially* serious and comes only from what the reporter ticked. No automatic text detection in the prototype.

## 9. PDF generation

1. Load the official `ADRRF_2.pdf` and fill fields via the field map (text at 8 pt, checkboxes set, "X" in tick cells, dates as dd/mm/yyyy).
2. Leave blank: AMC Report No., Worldwide Unique No., Reg/IPD/OPD/CR No., receiving-personnel name/signature, causality column, reporter signature (for handwriting). An automated test fails if any of these ever gets a value.
3. If there are more than 4 suspected medicines, more than 3 concomitant products, or text too long for its box, add a **continuation page** with the overflow, labelled with the case reference.
4. Stamp a small internal reference **outside** the official fields, in the bottom margin, e.g. `Internal ref ADR-001 · v2 · generated 22/10/2026`.
5. Until approval, add a light diagonal watermark: **DRAFT – NOT FOR SUBMISSION**. The approved version is frozen (form flattened, stored, never regenerated with different data).
6. Keep page 2 (official reporting advice) unchanged.
7. **Tests:** fill → read back every field → compare with the input. A visual check is done against the blank official form.

## 10. AI prescription demo (step 6, after the workflow is accepted)

**Flow:**
1. In section C (Suspected medication) the reporter clicks **Extract from prescription** and uploads a JPG, PNG or PDF (max 10 MB). The file type is checked by its content, not just its name, and the file is stored privately.
2. The server sends the file to Claude, which must return JSON matching a Zod schema. For each medicine it returns:
   - name, strength, dose, route, frequency, start date, duration
   - manufacturer, batch and expiry (usually *absent* on prescriptions, so these come back empty; that is expected and shown honestly)
   - the exact text it read
   - an "uncertain" flag for unclear writing

   The instructions forbid guessing: anything not visible comes back empty.
3. **Verification screen:** the document preview sits next to the proposed values.
   - Each value can be **accepted**, **edited** or **rejected**. Uncertain values can't be accepted without an explicit tick.
   - Each medicine is marked as either **suspected** or **concomitant**. The AI never decides which drug is suspected.
   - Nothing enters the report until **Add to report** is clicked.
4. Accepted values fill the medicine rows. Each one records "Source: prescription.png (AI-extracted, verified by …, time)".
5. The reviewer's right-hand panel shows the original document and which values came from it.

**Safeguards:**
- No API key configured: the button reads "AI extraction unavailable – enter details manually".
- Refusals, unreadable output and errors produce a clear message, never a partial silent fill.
- Only fictional prescriptions are used. A real deployment would need approval before sending patient data to an external AI service.

**Fictional samples:** 2–3 prescription images created for the demo and watermarked *FICTIONAL*. One is clean, and one is a harder, lower-quality "scan".

**Tests:** automated tests use a saved example response, so they make no API calls and cost nothing. One live check is run with your key.
